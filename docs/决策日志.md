## 2026-09-15 · 入口方案：全局快捷键 + 悬浮球可选开关（已实现）

**用户的判断（原话）：** 「我感觉悬浮球不是入口的最优解。」希望保留悬浮球但改为用户选择性开启，同时加全局快捷键。

**预期：** 若 ② 断点的主因确是发动成本，连续 14 天验证的完成度应显著提升。

## 2026-09-15 · 日期解析修正：正则优先，模型兜底

**触发（用户原话）：** 「我的AI不知道明天是几号，比如我在快速记录中写道 物理测试 明天 19：00，它默认到 3023-04-17」

**证据（实测，非推断）：**

- 复现了同类错误，但**没能复现 3023 这个具体值**（模型有随机性）：同一句「物理测试 明天 19：00」实测返回 `2023-12-04`；「下周三交报告」返回 `2023-05-24`；「9月30日前报销」返回 `2022-09-30`。都是把**训练数据的时间当成了"现在"**。
- **根因：`PARSE_SYSTEM` 里没有任何「今天是几号」的信息。** 模型只能自己编。
- 加一句日期锚后，6 个用例全部落到正确的 2026 日期。但「下周三」模型给 `2026-09-21`（周一），正确应为 `2026-09-23` —— **日期算术仍不可靠**。
- 顺带查出两个同源问题：
  1. `parseChineseDate()` 的「下周X」也算错（今天是周二，「下周三」算成明天 9/16）。
  2. `entry.time` 字段在提醒调度（`main.js:449`）、首页、历史里**早已全链路支持**，但 `parseEntry()` 从不产出 `time` —— 用户写的「19:00」被直接丢掉，提醒退化成当天 00:00。

**选择：** 日期以**正则为准，模型只兜底**；`time` 纳入解析并在保存时落库。

**理由：** 常见中文日期表达是确定性的，不该交给一个 9B 模型做算术。正则认不出的表达（「国庆前」「下个月初」）才交给模型，并用 `sanitizeAiDate()` 挡掉越界年份（`y < 今年-1 || y > 今年+10`）。

**可逆性：** 高。纯逻辑改动，`git revert` 即回滚；已存记录不受影响。

**验证：** 41 条断言全部通过（含真实模型端到端 6 例、「19：00」全角冒号、非法时刻拒绝、编造年份拦截）；6 个改动文件语法检查通过。
**未验证：** main.js 里 `updated.time` 的落库——需要重启 app 才能在真实链路上看到。**（当前进程跑的还是旧代码。）**

**教训（记下来）：** 这次不是「加功能」，是补一个**核心循环 ③ 的漏**。而它一直都在——只是**用户第一次真正用，就撞上了**。此前 7 天没启动过 app，所以这类问题不可能被发现。**验证轨的价值，在这一次体现出来了。**

**新增待决（本条暴露）：** 默认提前 24h 提醒 → 下午记的「明天 19:00」会在保存后**立刻弹通知**。此现象在我改动前就存在（只是提醒文案更不准），改动后更明显。是调小 `remindLeadHours`，还是改成「距截止不足 lead 就不提醒」？

## 2026-09-15 · 便签：空便签不再落库 + 退出历史页默认视图

**触发（用户原话 + 两张截图）：** 「就是这种，直接记入了历史记录」——截图是一张**空白的新便签**，和历史页里一条**没有内容的「便签」记录**。

**查数据后发现的真因（不是「便签出现在历史页」这么简单）：**

```
 0 | "便签" | sticky=true | content长度=0   ← 空
 3 | "便签" | sticky=true | content长度=0   ← 空
 6 | "便签" | sticky=true | content长度=0   ← 空
 7 | "便签" | sticky=true | content长度=0   ← 空
 8 | "便签" | sticky=true | content长度=0   ← 空
 9 | "测试" | sticky=true | content长度=2   ← 6 条里只有这条真写了字
```

`createStickyWindow()` 在**点「新建便签」的那一刻**就 `data.push(noteEntry)` 并写盘（`title:'便签'`、`content:''`）。所以**开一张便签、什么也不写、关掉，历史页就永久多一条空的**。用户 15:04–15:06 两分钟内开了 3 张，就攒了 3 条。这是 bug，跟「历史页要不要显示便签」是两件事。

**选择（用户两项拍板）：**

1. **空便签不是记录**——便签只有在真正写了东西之后才落库；写了又全删光的，把那条记录删掉。
2. **历史页默认不列便签**，加一个「便签」筛选 chip 单独调出来。

**理由：**

- 前者的根子是「记录的生命周期由窗口创建驱动，而不是由内容驱动」。窗口开过 ≠ 有内容。顺着这条，顺手也堵掉了 `noteId = noteId || 'pending'` 这个哨兵值——它在首次保存回包到达前会把 `'pending'` 当成真 id 发回去，主进程找不到就**再建一条**，是同一类重复记录的隐患。
- 后者是我上一轮判断错了。我当时保留便签在历史页，理由是「重启后没有别的入口能打开旧便签」；但用「默认隐藏 + 一个 chip 调出来」同时满足两边——既不混进列表，又保底找得回。**用户的原始诉求一直是「便签别混进别的列表」，我上一轮把它读窄成了「别混进待办」。**

**具体改动：**

- `main.js`：抽出 `newEntryId()` / `ID_SHAPE`；`createStickyWindow(null)` 只分配 draft id 占窗口槽位，**不写盘**；`note-save` 改为首次保存才建记录（用 draft id，形状校验过才认），正文与标题都为空时不建，已存在则删除；回包加 `created` 区分首次落库。
- `notes.js`：`saveNow()` 不再自己判空、不再有 `'pending'` 哨兵；标题兜底移到主进程；首次保存才显示时间戳（沿用 `created`）。
- `history.html` / `history.js`：状态 chip 组加「便签」；`全部/待办/已完成` 三个视图一律排除便签，只有「便签」视图显示。
- **存量清理**：删掉那 5 条空便签（备份 `data.json.bak-2026-09-15T15-19-06-363Z`，回读校验：非便签条目与有内容的便签逐字节未变，备份可还原）。

**可逆性：** 高。`git revert` 单次提交即可回到旧行为；存量清理有备份文件，且**删掉的 5 条本来就全是空的**。

**验证：**
- 把 `main.js` 里**真正的 `note-save` 处理器源码切出来**，喂给假的 `ipcMain`/数据层跑了 7 个场景 21 条断言（开而不写不落库、首存用 draft id、续写不产生第二条、写完删光会删记录、怪 id 被挡下、不误删非便签记录），全通过。
- `history.html` 在真实浏览器里起真身（运行时复制真身的标记与样式，只换 `api`）：默认 `共 3 条记录` 且便签不在其中；点「便签」→ `共 1 条记录` 只有那张便签；四个 chip 高亮与筛选互相不串；便签卡片上只剩 `[复制][删除]`，无「转为待办/改期」，标签为「便签」；与分类/标签筛选叠加正常。

**未验证：** 便签窗口里的实际观感（「已保存 + 时间戳」只在首次出现），需用户手动确认。

**待决（本条新增）：** 用户真实数据里还剩 1 条有内容的便签（「测试」）。它现在只能在历史页的「便签」chip 下找到——**「重新打开便签」的入口仍然没有**，这是上一轮就记下的待决项，本轮只是让便签不再污染默认视图，没有真正解决它。

## 2026-09-15 · 便签重新定义为「不参与待办体系的自由记录区」

**触发（用户原话）：** 「目前在快速记事区和便签区记事都会被记入代办事项。但我现在想让便签区写入的事件不进入代办事项，同时在便签区的顶部左上角给一个下拉窗口，供用户选择已经存在的任务直接按条目选入便签内容中。」

**先做了一次前提核实，结论与用户的描述不符：**

- 用户补充说明「就是新建便签，向其中填写内容，内容会被自动判定至代办」。**这经不起核对。** 全仓库只有三处会把 `status` 置为 `pending`：`main.js` 快速记录的 AI 回填、`make-pending`（首页「转为待办」按钮）、`update-due-date`（「改期」按钮，**设了日期就自动升级**）。而 `note-save` 全文**没有任何 `ollama` 调用**，新便签一律落 `status: 'note'`。
- **实测用户当前的 `data.json`（9 条）：5 条便签没有一条是 `pending`**，全为 `note`/`done`。唯一进过待办的那条（`note` → 设了 9/11 → `done`）只能来自「改期」这条隐形升级路径。
- **所以用户看到的是：** 新建便签 → 它出现在首页「记录」页的「最近记录」栏 → 该栏就在「待办事项」正下方，且卡片上明晃晃写着「转为待办」。读起来就是「我的便签被归进待办了」。

**选择：** 不管机制是「自动」还是「按钮触发」，按用户要的结果做——**便签彻底退出待办体系**，并在数据层加护栏。

**具体改动：**

1. 判据收敛为一个函数 `isTodo(e) => e.status === 'pending' && e.sticky !== true`（`main.js`），替换 6 处散落的 `status === 'pending'`：角标计数、提醒调度、最近记录、AI 对话上下文、首页仪表盘、待办列表。**「改一处要同时改另一处」的地方都用注释互相指了路。**
2. 堵掉两条隐形升级路径：`make-pending` 拒绝便签；`update-due-date` 对便签只存日期、不改状态。
3. 历史页：便签保留（**因为它是唯一兜底**），但不再渲染「转为待办」「改期」，状态标签显示「便签」。
4. 便签左上角的装饰性圆点换成「选入已有任务」按钮，点开是一个覆盖内容区的浮层：筛选框 + 待办列表，点一条即往正文末尾追加 `- 标题（9/16 19:00）`，走现成的防抖保存。**没有新增任何 IPC**——复用了 `get-entries` / `entries-changed`（主进程本来就广播给所有窗口）。

**理由：** 「便签」和「待办」是两件事。便签是**落笔即忘**的自由区，待办是**要被提醒**的承诺。混在一起的代价是：用户不敢在便签里随便写，因为写了的东西会变成承诺。而护栏放在数据层而不是只藏按钮，是因为**路径会增殖**——今天堵掉 UI 上的两个按钮，明天加个批量操作就又漏了。

**可逆性：** 高。`git revert` 单次提交即可；**无数据迁移，没有改动 `data.json` 里任何历史条目**（含那条 `便签/done/2026-09-11`，按「改用户数据不在本次范围」保留）。

**验证：** 用用户真实的 `data.json` 跑断言（只读，跑完比对字节确认未被改动）：便签漏出 0 条；**首页「最近记录」8 条 → 3 条（5 条便签全部移出）**；待办数 1 → 1（不受影响）；下拉候选集实测渲染为 `- 物理实验（9/16 19:00）`。
**未验证：** 窗口内的实际观感（浮层高度、点选手感），需用户手动确认。

**新增待决（本条暴露）：** `openNewSticky()` 永远传 `null`，`createStickyWindow(entry)` 的 entry 分支虽存在却无人调用——**app 重启后没有任何入口能重新打开一张旧便签**。历史页现在是唯一的兜底。是否要一个「重新打开便签」的入口？

**取舍记录：** 便签窗口固定 240×230，浮层可用高度约 206px（筛选框 + 约 5 行）。**没有做「打开时临时加高窗口」**——那要新的 resize IPC，且本仓库多处已记录 Windows 透明窗口改尺寸的钳制怪癖。用户实际用起来觉得挤再加，那是一个独立、可逆的小改动。

## 2026-09-20 · 便签「选入已有任务」改为勾选式，条目落进正文

**触发（用户原话）：** 「我想要重构目前的便签贴：1. 便签贴的UI保持 2.便签贴在顶部构建一个下拉选项（或者在输入框使用/符号）唤出一个下拉列表，列表中是所有的代办事项，用户勾选后能够显示在便签贴上 3. 便签贴取消输入事件记入代办事项的功能，现在便签贴不可向代办列表中加入代办事件」

**先做了一次前提核实，第 3 点已由 `fe574d8` 达成，本轮零改动：**

- `note-save` 全文没有任何 AI 调用，新建便签一律落 `status: 'note'`；`make-pending` 与 `update-due-date` 两条升级路径都对便签关闸。
- 判据收敛在 `isTodo(e) => e.status === 'pending' && e.sticky !== true`，6 个入口全走它。
- **实测用户当前 `data.json`（3 条，2 条便签）：便签漏进待办体系 0 条**，两条便签 `status` 均为 `note`。跑完比对字节，`data.json` 未被改动（只读）。

**澄清后拍板（AskUserQuestion）：** 勾选形式 = **正文里的勾选条目**（`- [ ] 标题（日期）`，与便签正文混排），不是独立的结构化字段；触发方式 = **顶部按钮 + 正文 `/` 两个都要**。

**选择：** 把原来的「点一条 → 关浮层 → 正文追加一行」改成「**多选勾选 → 正文出现 `- [ ]` 条目，再勾一次即删掉该行**」，并补 `/` 触发。

**理由：**

- **勾选状态由正文文字派生，不新增字段、不新增 IPC、无数据迁移。** 代价是正文被手改后勾选态会漂移（改掉日期尾巴就认不出了）——**已当面说明并接受**。换取的是：便签仍然只是一条 `content` 字符串，`note-save` 一个字都不用改。
- `/` 只在**行首**触发并吞掉该字符。行中的 `/`（`9/16` 这种）不拦——这是个真实存在的写法冲突，行首规则是目前最省事的划界。

**具体改动（全在 `notes.html` + `notes.js`）：**

- `lineFor(e)` 生成条目行；`lineMatches(line, e)` 判一行是否属于该待办（`- [ ]` / `- [x]` 都认，日期尾巴需一致）；`isPicked(e)` 由正文派生勾选态；`insertLineAt(body, line, pos)` 保证条目独占一行。
- `insertTask` → `toggleTask`：已在正文则删该行，否则在 `insertPos` 插入；**浮层不关**（多选）。`insertPos` **随插入往后挪**——否则连勾多条会次次插在同一处、把后勾的顶到前面。
- `renderPickList` 每项前加勾选框；`aria-selected` 改挂「是否已勾」，键盘高亮改由 `aria-activedescendant` + `data-active` 承担，容器加 `aria-multiselectable="true"`。两者职责分开，互不抢位。
- `/` 触发：`bodyInput` keydown，光标在行首时 `preventDefault()` 后 `openPicker(caret)`；顶部按钮触发则 `insertPos = 正文末尾`。
- `notes.html` 只加了勾选框的 CSS 与 `aria-multiselectable`，**其余 UI 一律未动**（用户的第 1 点）。

**验证（起便签真身：运行时复制 `notes.html` 的标记与样式，只把 `api` 换桩，跑的是真实 `notes.js`）：** 46 条断言全部通过（43 条交互 + 3 条真实数据只读）。

**验证过程抓到两个真 bug（都不是靠读代码看出来的）：**

1. **点一下勾选，浮层就被关掉。** `toggleTask` 会重渲染列表，被点的那一项在事件冒泡到 `document` 之前已经**脱离文档**，于是「点外面关闭」里的 `pickPanel.contains(target)` 返回 `false`。修法是在 `pickList` 的处理器里 `e.stopPropagation()`，并把原因写在注释里。
2. **连勾三条，正文里的顺序是反的。** `insertPos` 在打开浮层时就被冻结，三次都插在同一处，后勾的顶到前面。修法是插入后把 `insertPos` 往后推。

**未验证：** 便签窗口内的实际观感（浮层在 240×230 里约 5 行是否够用、勾选手感、`/` 的触发是否顺手）——Electron 桌面窗口无法被浏览器预览工具观察，**需用户手动确认**。浏览器验证台复刻的是真身标记 + 真实脚本，但仍是浏览器环境。

## 2026-09-29 · 修「显示 AI 在线，提问却没响应」——失败原因透传 + 超时分层

**背景（截图实证，顺序本身就是证据）：** 用户问「我今天有什么安排？」，先跳出 AI 气泡
「本地模型似乎没有回应，请确认 Ollama 已启动后再试一次。」，**紧接着**又跳出一条
「本地模型暂时不可用，请确认 Ollama 已启动」。而右上角一直写着「AI 在线」。
先超时、后空回包 —— 说明主进程处理超过了 30 秒，且最终返回了 `null`。

**根因（六条，互相叠加）：**

1. **每条消息跑两次串行生成。** `main.js` 先 `extractTaskFromMessage()`（判断「这是不是创建任务的指令」，一次完整生成），
   成功后才 `chatReply()`（第二次完整生成）。本机实测：温态 7.1s + 5.2s = **12.3s**，冷态（含 8s 模型加载）**14.2s**。
   这只是 2 个字的回复 + 空待办清单；真实场景要生成一长串待办摘要，冷盘读 6.3GB 权重，`>20s` 是常态。
2. **超时预算错配。** 单次调用 20s，后端最坏 `extract 20s + chat 20s = 40s`，
   而前端兜底定时器只有 **30s —— 比后端最坏值还短 10s**，所以必定先谎报离线。
3. **`fetchWithTimeout` 的超时管不住读 body。** 它在 `fetch` 一返回就 `clearTimeout`，
   而 `await res.json()` 是**调用方**才做的 —— 20s 只覆盖「连上」，不覆盖「读完」。
   已用假服务器实测（发响应头 + 半截 body 后永不结束）：**旧实现 3 秒内不返回，永久卡死**。
4. **四种失败压成一个 `null`。** 配置的模型没装（404 `not found`）、兜底选中嵌入模型（400 `does not support chat`）、
   fetch 被 abort、模型返回空文本 —— 全部返回 `null`，上层唯一能说的话就是「请确认 Ollama 已启动」。
   服务明明在跑时，这是**自相矛盾的假信息**，用户照着做也修不好。
5. **「在线」的判据本身不成立。** `isAvailable()` 只 `GET /api/tags`，**服务可达 = 在线**，不问配置的模型在不在、能不能 chat。
6. **兜底必然选中嵌入模型。** 兜底取 `models[0]`，而 `/api/tags` 的顺序里 `qwen3-embedding:latest` 恰好排第一。

**选择：** **保留两次调用结构**（代价是任务类消息慢一倍，但换来「AI 能自己判断要不要建待办」），
只修超时预算与错误透传。

**具体改动：**

- `ollama.js`：`fetchWithTimeout` → **`fetchJsonWithTimeout`**，把 `await res.json()` 放进同一个 `try`，
  abort 计时器到解析结束才清；**但 abort 必须往上抛**——第一版把 `AbortError` 和 JSON 解析失败一起吞了，
  于是「body 读到一半被掐断」被误判成「模型回了空白内容」（这条是写完测试才发现的）。
- 超时分层：探测 `/api/tags` 3s（本机 HTTP，超时即离线，要快）/ `generate()` 60s（冷加载 + 长 JSON）/ `chatReply()` 120s。
- `chatReply` 返回 `{ok, text, reason}`，`reason ∈ model_missing / no_chat_model / timeout / http / empty`；
  `main.js` 按 reason 给各自准确的文案，点名是哪个模型没装。
- 新增 `listChatModels()` / `probeChatModel()`：按 `/api/tags` 的 `capabilities` 含 `completion` 过滤，
  旧版 Ollama 无此字段时退化为名字黑名单（含 `embed`）。兜底改为在**能对话的模型**里最多试 3 个，命中即写回 `MODEL`。
- 头部改三态（`online` / `warn` 无对话模型 / `offline`），设置下拉框只列能对话的模型。
- 前端 30s 兜底保留（它存在的意义是解卡），但**只说「还在生成中…」，不改状态、不判离线**。

**验证（假 Ollama 实测，不是读代码）：** 起一个可编程的假服务复现每种真实失败，跑 16 项断言全通过 ——

## 2026-09-29 · 修「点截止日期后底部全黑」—— 用固定延迟去等渲染时序，在刷新率不同的机器上会得到相反的结果

**背景（截图）：** 点「截止日期」后窗口已按预期扩到 440×520，结构化表单都在，**下面一大片纯黑，日历完全不见**。
黑就是暗色主题的 `--surface-panel: #111111`。

**根因（预览器里确定性复现）：** `positionPop()` **用 `display` 归零来做测量**，且**靠调用方恢复**：

```js
popEl.style.visibility = "hidden";
popEl.style.display = "block";
const popH = popEl.offsetHeight;
popEl.style.display = "none";     // ← 量完就藏；恢复 display 是调用方的责任
popEl.style.visibility = "";
```

全文件里**只有一处**恢复它 —— `openPop()` 的双 rAF 回调。而 `reposition()` → `positionPop()`
**没有恢复**。调用方 `index.js` 在窗口扩张后调了它：`setTimeout(() => reposition(), 30)`。

**这就是一条竞态，而且在这台机器上必然输：** 双 rAF 在 240Hz 上约 8ms 跑完（实测 `CurrentRefreshRate = 240`，单帧 4.2ms），
比 30ms 的定时器**早 22ms** —— 于是定时器把刚显示出来的日历又藏掉，再也没人恢复。
**60Hz 下 rAF #2 在 ≈32ms，反而晚于定时器，结果是可见的** —— 这正是此前测不出来的原因。

**选择：** 让 `display` 的**所有权唯一**，并干掉「猜一个延迟」。

1. `positionPop()` 不再拥有 `display`，任何时刻调用都只写 `left/top/width`，不可能把弹层藏掉。
2. `openPop()` 先 `display:block` + `visibility:hidden`（可量不可见）→ 双 rAF → 定位 → 揭晓。
3. **用 `ResizeObserver` 观察 `.nsdp-cal-host` + `window.resize` 取代 `setTimeout(…, 30)`** ——
   后者既不可靠（本轮 bug 就是它引起的），又解决不了 React 的异步提交：
   `date-picker-react.js` 用 `createRoot().render()`，双 rAF 时可能只量到占位高。
4. 顺手修两处相邻缺陷：`aria-expanded` 建好即 `"false"` 之后**没有任何地方置 `"true"`**（屏幕阅读器判断开合的唯一依据一直是错的）；
   `calIcon()` 的 `stroke-width:1.8` + 圆头违反图标合同（DESIGN.md 要求 2px 方头 + `crispEdges`）。

**理由（这条要沉淀的是教训，不是修法）：** **用固定延迟去等一个动画/渲染时序，在刷新率不同的机器上会得到相反的结果。**
同一个 `30ms`，在 60Hz 上是「等到了」，在 240Hz 上是「来不及」—— 而代码看起来一模一样，
在本机复现不了的现象，在用户机器上每次必现。**能观察就观察，别猜。**
（`ResizeObserver` / `window.resize` 是「事件驱动」，`setTimeout` 是「猜」；
前者在任何刷新率下都对。）

**验证：** 预览器里重复复现脚本，确认 `reposition()` 之后 `display` 仍是 `block`；
亮/暗两主题扫描通过。**真机（`npm start`）已跑：240Hz 上点「截止日期」后 `display` 再没回到 `none`，
弹层从 `top=4` 重定位到 `top=121`，日历完整可见 —— 见本日最后一条。**

**代价：** 日历弹层多两个观察者（`ResizeObserver` + `window.resize`），`closePop` 里要 `disconnect()`。
比一个 `setTimeout` 复杂，但换掉的是「在别人的机器上必现的 bug」。

**可逆性：** 高。`git revert` 即可。

## 2026-09-29 · 修「对话正文里显示思维链」—— 上一条修复的副作用

**背景（真机实测，不是推断）：** 本机 Ollama 上 4 个模型，`capabilities` 为
`qwen3-embedding` = `["embedding"]`、MiMo-VL / glm-4-9b = `["completion"]`、`qwen2.5:7b` = `["completion","tools"]`。
直连 `chatReply()` 时，落到 `XiaomiMiMo_MiMo-VL-7B-RL-2508-Q4_K_M` 返回的 `text` **就是原始思维链**
（`<think>\n嗯，用户问的是今天的安排，我需要先回忆上下文里有没有日程记录。…`，句子断在中间）；
同一次测试里 `glm-4-9b-chat-1m-Q4_K_M` 的回复是干净的。

**这是上一条的副作用，不是新引入的独立 bug。** 修「AI 在线但没响应」之前，`chatReply` 的兜底会选中
`models[0]`（恰好是嵌入模型），拿到 HTTP 400 直接失败 —— 推理模型**根本没机会说话**。
兜底改对之后，推理模型第一次真正跑起来，它的 `<think>` 才浮到用户面前。
**教训：修好一条「走不到」的路径，等于把那条路径上所有的旧毛病一次性激活。**

**根因（两道）：** 一是**模型把思维链当普通文本吐**：MiMo 的 `<think>` 就在 `message.content` 里，
不归 Ollama 的思考模板管；二是**拿到的文本没做任何规整**就直接返回给上层当答案。

**选择：** 两道防线都做 —— **先试参数（`think:false`），再做字符串规整**，而不是二选一。

**理由（对着实测数据做的决定，不是「保险起见」）：**

- `think:false` 是 Ollama ≥0.9 的 `/api/chat`、`/api/generate` 参数。实测本机 0.32.13 上，
  连**不思考的**模型（glm / qwen2.5）也照单全收、不报错，参数是白给不是负担。
- 但它**关不住 MiMo**：带上 `think:false` 之后 `content` 里**照样**是 `<think>…</think>`。
  所以 `stripThinking()` 不是「保底」，**它才是主力**；参数只负责掐掉 qwen3 / deepseek-r1 那类
  真·思考模型的思维链开销（顺带省掉它们吃掉 120s `CHAT_TIMEOUT` 预算的风险）。
- 判据取「有没有**配对**」而不是「有没有出现过 `<think` 字样」：这是用户明确要求的
  「先看是不是配对的完整块」。**没闭合的标签就是分水岭** —— 它前面什么都没有（整段是没写完的
  思维链，返回 `''`）还是已经有正文（多半是正文里在讨论这个标签，一个字不动）。

**顺带确认的第三条路径（`/api/generate`）：`extractJson` 确实会中招，而且有两种形状。**

| 形状 | 旧 `extractJson`（首 `{` 到末 `}`） | 后果 |
|---|---|---|
| 思维链 + 答案都在 | 首 `{` 落思维链、末 `}` 落答案 → 跨段解析失败 → **`null`** | AI 解析**静默失效**，整条路径悄悄降级成正则兜底，用户看不出「AI 白装了」 |
| 思维链被掐断（没答案） | 首末 `}` 都落在思维链复述的**提示词示例**上 → **`{"title":"开会","dueDate":null}`** | **安静地写下一条假任务** —— 不报错，只是把错数据存进库 |

第二种尤其危险。修复放在 `generate()` 返回值这一处收口，`parseEntry` / `extractTaskFromMessage` /
`classifyEntry` / `generateReminder` 四条路径同时受益；剥完为空则返回 `null`，让确定性正则接手。

**具体改动：**

- 新增 `stripThinking()`（`ollama.js`）：成对块（跨行 / 大小写 / `<thinking>` / 带属性）整块删；
  删完整段以没闭合的 `<think>` 开头 → 返回 `''`；没闭合的标签前面已有正文 → 原样保留。
- 新增 `postJson()`：统一带 `think:false`；**老版本 Ollama 不认这个字段会回 400**，
  撞上就永久关掉开关、去掉参数重发一次（只重发一次）。退路取交集而不是靠状态码猜 ——
  嵌入模型的 400 是另一回事，去掉 `think` 再撞一次后仍按原逻辑分类。

  旧写法在后者直接 `return empty`，等于让一次截断把整轮对话判死，而隔壁 glm 明明好好等着。
- `main.js` 的 `empty` 文案改写（两种成因合并在这一个 reason 里，要把「换个模型」这条可操作的路指出来）。

**预期与验收（真机跑本机真实模型）：**

| 场景 | 实测结果 |
|---|---|
| MiMo 作配置模型 | `ok=true`，`text` 无 `<think>`、是完整句子（对照：同一 prompt 的原始 `content` 771 字、含 `<think>`/`</think>`） |

| 假 Ollama：候选**都**只吐思维链 | `ok=false reason=empty`，`text` 里**绝不出现**思维链 |

实测是 **`null`** —— 首 `{` 在链里、末 `}` 在答案里，跨了整段导致解析失败。

本机 4 个模型实测都不产生这种形状。已记入待决清单。

**可逆性：** 高。`git revert` 即可，不碰数据、无迁移。外部契约只多了一个导出（`stripThinking`，给测试用）。

`HTMLElement.click()` 只派发一个合成的 `click`，**根本不经过 pointerdown → mousedown → pointerup → mouseup**。
而这个 bug 全部发生在 pointerdown 之后的改派上，那条路径被完整绕开了。
**这一轮最该记住的一条：验证手段如果跳过了真实的输入序列，等于在测另一个程序。**

**根因（`index.js:149-160`，一行判断写错了对象）：**

输入面板整块是可拖拽区，`setupDrag(inputContainer, …)` 在 pointerdown 里无条件
`inputContainer.setPointerCapture()`。**指针捕获之后，该指针的后续事件全部改派给捕获元素** ——
`pointerup`/`mouseup` 的 target 变成 `#input-container`，而 `click` 按规则派发到
down 与 up 两个 target 的**最近公共祖先**，也就是 `#input-container`。

为了让控件不被误拖，紧跟其后有一个捕获阶段的拦截：

```js
const tag = e.target.tagName;
if (tag === 'INPUT' || tag === 'SELECT' || tag === 'BUTTON' || tag === 'TEXTAREA') e.stopPropagation();
```

**它判断的是按下的那一点落在什么 tag 上。** 而日期字段是 `date-picker.js` 注入的：

```html
<button id="f-due-field"><span class="nsdp-field-value">截止日期</span></button>
```

按在文字/图标上时 `e.target` 是内层 **SPAN**，不匹配任何一条 → 拦截失效 → `setupDrag` 照常捕获
→ 字段自己的 `click` 收不到 → `togglePop` 从不执行 → **日历不开**。

**这也解释了「要点好几次」**：只有按在按钮**内边距/边框**上时 `e.target` 才是 BUTTON、拦截才生效，
那一下才会打开。字段可视面积几乎全被内层 span 占满，所以绝大多数点击失败、偶尔成功。

**为什么只有日历中招：** 四个控件里，只有 `#f-due-field` 的可视内容不是控件本身 ——
`<input>` / `<select>` / 两个保存按钮 / 两个 tab 都是纯文本，`e.target` 就是它们自己。
**全仓库只有这一个控件的 tag 判断会漏**，与用户只报日历完全吻合。

**修法 —— 把「看 tag」换成「看祖先链」：**

```js
if (e.target.closest('input, select, button, textarea')) e.stopPropagation();
```

`closest()` 会穿过 span 找到外面那个 button。判据从「按下的那一点是不是控件」
变成「按下的那一点是否落在控件内部」—— 这才是原本想表达的意思。

**验收（真机 Electron，走 CDP `Input.dispatchMouseEvent`）：**

> 用的不是 `field.click()`，而是真实的输入管线：pointerdown/mousedown/pointerup/mouseup/click 齐全。
> **没有用操作系统级鼠标注入** —— 本机鼠标正被真实用户占用（实测光标会自己移动、窗口位置会漂），
> OS 注入会把「窗口在 down 与 up 之间移动」混进来，**制造出一个假的「pointerup 打到别的元素」**。
> 这一点单独记一笔：我第一轮正是被这个假象带偏了。

**修前基线**（同坐标、同一毫秒）：`pointerup` 的 target 已经是 `#input-container`，
而那一刻 `elementFromPoint` **仍然指着字段内的 span** —— 命中测试与事件目标对不上，
这就是「被改派」而不是「元素移动了」的铁证。`click` 落到 `#input-container`，`pop` 保持 `false`（连点 3 次都不开）。

**修后：**

| 场景 | 实测 |
|---|---|
| 首次单击 | 弹层 `display` 从未创建 → **`block`**，`aria-expanded` false → **`true`**，窗口 420×190 → **440×520** |
| 点日历里的某一天 | 值变为 `2026年9月17日`，`display:none`，窗口回到 420×190 |
| 再点一次 / 再点一次 | `block` → **开**；`none` → **关**（单击切换正常） |
| 面板空白处拖 (60,40) | 窗口 (310,842) → (370,882)，精确 +60/+40 —— **拖拽没被弄坏** |
| 控件上按下并拖 (60,40) | 窗口 (370,882) → (370,882)，**纹丝不动** —— 控件仍不被误拖 |

截图确认：单击一次后日历完整渲染（2026年9月、日格、今日高亮），下方无黑块。

**没动的地方（是取舍，不是遗漏）：** 没有改成「先滑够阈值再 `setPointerCapture`」。
那样确实更「正确」，但 `setupDrag` 同时被悬浮球、主页、便签复用，改它的行为要连带回归三处拖拽；
而这里真正写错的是拦截判据本身。**改动面越小，越能确定修的是这个 bug。**

**可逆性：** 极高。`index.js` 一行判断，`git revert` 即可；不碰数据、无迁移。
无新增文件，`pack.bat` 不用改（`index.js` 本来就在拷贝列表里）。

1. **右栏数据全部取自真实记录**，不摆假样本。`latestStructured()` 取真条目，`dueMoment()` 与主进程

2. **主题改成即点即生效**（这是唯一一项）。理由是它不像提前量或模型，看名字判断不了要不要，
   必须看见才知道。走新加的 `preview-theme` IPC **只调 `nativeTheme.themeSource`、不写 `config.json`**，
   「取消」/关闭时把进来时记下的值再翻回去 —— 于是这不是「撤销一次写入」，

3. **右栏表头刻意造成左栏组标题的样子**（编号 + 吸顶 + 下边线），文字与左栏那一行**逐字相同**。

4. **05 数据是唯一一组只读设置**：条数 / 分区计数 / 占用 / 最后写入 / 存储路径 +「打开存储文件夹」。

   `ollama.js` 的 `OLLAMA_HOST || 'http://127.0.0.1:11434'`。

**复盘 —— 两个假阳性，都是同一类错：**

- **`transition: none !important` 必须写成 `*, *::before, *::after`。**

## 2026-10-01 · typeset：把行高与字距从「散在各元素上」收成「按面 + 层级给」

**背景。** `DESIGN.md` 的排版节把**字面**（两套字体按作者分工）、**字级**（锁 12 的整数倍）、
**字号下限**（13px）、**字重**（点阵恒 400）都写死了 —— 唯独**行高**和**字距**一个字没提。
漂移就全藏在这两条没写下来的地方。这不是巧合：**没有成文的地方，就是没人守的地方。**

**查到的四处（都是实测值，不是读代码猜的）。**

1. **`.mod-code` 一个角色、四种渲染。** 页头 `normal|18px`，卡片 `.card-label` `0.48px|16.8px`，
   列表 `h2` `0.72px|18px`，页标题 `h1`、设置标题 `h3` 各又不同。
   根因是它自己既不声明 `line-height` 也不声明 `letter-spacing`，落在谁家就吃谁家的；
   而 `homepage.html` 里还额外有三处 `line-height: 1.4` 的就地补丁在改它。
   **同一个方块，在同一个应用里长成四样。**

2. **13px 正文档四个行高**：`1.5`（`.desc` / `.entry-content` / `.chat-msg`）、
   `1.6`（`.see-note` / `.see-src`）、`1.7`（`.see-line` / `.see-empty`）、`normal`（若干单行标签）。
   其中 `.see-line` 是「键 / 值」单行对，用 1.7 是最松的一档 —— 行距本该由它已有的
   `margin-bottom: 6px` 给，不该由行高给。

3. **24px 点阵显示层三个行高**：`1.2`（页头 `h1` / 设置 `h3`）、`1.3`（`.see-big`）、
   `normal`（`.tag-detail .big`，不写就是字体度量 32px）。

4. **同一屏上相邻两节的标题字距不同**：`.tags-label` 是 `0.04em`，`.list-section h2` 是 `0.06em`，
   两个都在仪表盘上、上下挨着。

5. **宋体正文出现孤字行**：设置页「截止前多久开始提醒，0 = 仅当天提醒」折两行，
   末行实测**只剩 1.5 个字**。中文没有词间空格，浏览器默认断行天生容易这样。

**两条查了但证伪的（记下来，免得下次重走）。**

- **「徽标高矮不一」是假的** —— `.set-group` 里的编号块量出 25.2、`.card-label` 里的量出 16.8。
  差 8.4px 看着像真缺陷。真因是我自己那套测量脚手架挂了 `zoom: 1.5`，
  设置面板在 zoom 里、仪表盘在 zoom 外：**25.2 = 16.8 × 1.5，27 = 18 × 1.5，全部对得上。**
  拆掉 zoom 再量，两种宿主都是原值。**教训：测量脚手架本身会造缺陷，换几何条件前先确认脚手架干净。**
- **「`.entry-title` 是伪粗体」是假的** —— 字栈尾部是 `SimSun`（无 600 字重），看着像会被浏览器合成。
  但栈**以 `system-ui` 打头**，`document.fonts.check('600 13px system-ui')` 返回 **true**，
  用的是真 600，宋体那一档根本没轮到。**看字栈要看第一个能解析的，不是看最后一个。**

**选择。** 行高与字距**按「面 + 层级」给，不按元素给**，写进 `tokens.css` 的 `--leading-*`：

| 层 | 值 | 判据 |
|---|---|---|
| 点阵单行 · 紧贴型 | `normal`（12px 上 = 16px 行盒） | 无边框无底色，实心贴住文字：编号块 / 按钮 / 组标题 |
| 点阵单行 · 徽标型 | `--leading-chip` 1.6 | 有边框或底色：`.due` / `.cat` / `.priority-*` / `.tag` / `.status` / `.chip` |
| 点阵显示层 | `--leading-display` 1.2 | 24px 标题与大单值 |
| 宋体正文 · 紧贴读 | `--leading-dense` 1.5 | `.desc` / `.see-line` / `.chat-msg` / `.dash-foot` |
| 宋体正文 · 成段读 | `--leading-read` 1.6 | `.see-note` / `.see-src` / `.see-empty` / 便签正文 |

紧贴型**故意不给 token** —— 显式写 `normal` 就是决定本身。
`--leading-chip` / `--leading-display` 各自把原来散着的 11 处和 4 处字面值收进去。
`line-height: 1` 只有两处保留，都是**定高容器**（定径圆环中心数字、16px 定高角标方框），
行高在那里不为排版服务，为的是让字形正好落进容器 —— 这两条不改。

字距统一：节标题一律 `0.04em`（`.list-section h2` 从 `0.06em` 改过来）；
`.mod-code` 自己声明 `letter-spacing: 0`，四处补丁删掉。

**孤字行**用 `text-wrap: pretty`（Chromium 117+，Electron 28 = 120）修。

**为什么行高按「面 + 层级」而不是按元素。** 按元素给就是现在这样：同一个方块四种渲染、
同一档正文四个行高。层级是有限的、能说清的；元素是无限的、说不清的。
**这条和 lshu「哪里用点阵集中写在选择器清单里」是同一条理由** —— 集中在一处，才守得住。

**实测复核**（预览器，真窗口几何 640×700，两套主题）：

| 项 | 改前 | 改后 |
|---|---|---|
| `.mod-code` 不同渲染 | 4 种 | **1 种**（`normal` + `0` 字距，8 处全同） |
| 徽标行高 | 1.6（字面 ×11） | 1.6（`--leading-chip` ×11），量得 36 条全 19.2px |
| 13px 正文档行高 | 4 种 | **2 种**（19.5 / 20.8），八行右栏逐行扫，`.`set-see` 里零个 `normal` |
| 24px 显示层行高 | 3 种 | **2 种**（28.8 与定高容器的 24） |
| 仪表盘两节标题字距 | 0.06em / 0.04em | **同为 0.48px** |
| 孤字行末行 | 1.0 字 | **2.0 字** |
| 两栏横向溢出 | 0 | 0（左栏纵向滚动 411 → 423px） |
| `detect.mjs --scope type` | `[]` | `[]` |
| 引用但未定义的 token | — | **0**（四个 `--leading-*` 全部解析） |

孤字行那条做了**同几何 A/B**（同一次运行里切 `text-wrap`，与之前的跨列宽比较不同）：
`pretty` 只动了那一条（1 → 2 字），其余六段断行**一字未变**（10/10、8/8、4/4、12.3/12.3、5/5、16/16）。
这是它该有的行为 —— 外科式，不是全局重排。

**预期。** 行高与字距此后只有五个值，且每个值都能说出它管哪一层。
新增元素时的问题是「它在哪一层」而不是「它该多高」。

## 2026-10-01 · polish：历史页收口 —— 一条被粘进来的长串就能把整页横着撑开

**靶子：** `history.html` / `history.js`，承接上一条 distill 的收口。
`critique-storage.mjs latest "history"` 返回 **EXIT=2**（没有历史快照），
所以按 polish.md 做了一遍独立走查，不靠既有评分。

**证据怎么取的：** 不靠 DOM 注入猜缺陷，而是把真实交互路径一条条走完 ——
空态（已完成 + `#联调` = 0 条）、便签视图、改期展开（日历弹层）、删除确认条、取消 / 确定。
预览器 mock 的写入方法只会重放既有数据（`setTimeout(() => fire('entries', clone()), 60)`）
**造不出新数据**，所以边界数据只能靠 UI 真实交互到达。

**唯一确认的缺陷：`.entry-title` 没有 `overflow-wrap`。** 粘一条 300 字无空格的串
（长 URL / Windows 路径 / base64 都长这样）进历史页：

| | 改前 | 改后 |
|---|---|---|
| `.entry-title` 宽（卡片 486px） | 2933px | 486px |
| `.content` 横向滚动条 | 有（2969 / 554） | 无 |
| 200 字中文标题高 | 96px | 96px（不变） |
| 16 条真实数据单卡高 / 列表总高 | 99px / 1587px | 99px / 1587px（不变） |

**为什么用 `anywhere`，不用主页面那套 `word-break: break-all`：** 实测同一句话
（`word ` ×12 + `Supercalifragilisticexpialidocious`）—— `break-all` 把行尾的长词砍成
`Supe` / `rcalifragilisticexpialidocious`，`anywhere` 整词移到下一行；
且 `anywhere` 对中文与普通英文的断行结果和 `normal` **逐行一致**（非侵入）。
标题绝大多数是中文、本来就断行，`break-all` 只会在行尾误伤英文单词。

**两屏标题契约不同是有意的，不统一。** 主页面 `.entry-title` 是
`nowrap + overflow: hidden + ellipsis`（「最近记录」栏，一行扫一眼，截断就对）；
历史页是**取回**记录的屏，标题就是全文，必须换行。

**查了但没动的（两处都差点误报）：**
- **取消 / 确定能否收行** —— 第一次测出「点了没反应」，是我的探针自己污染了状态
  （先误点了日历里那个无文字的清除按钮，又留下过期的 `.due-edit-row`）。
  清干净重测：点取消后 `rows: 0`、弹层关闭、字段移除，确定同理。**功能是好的。**
- **日历弹层「不显示」** —— `document.hidden: true`（预览面板在后台）会挂起
  `requestAnimationFrame`，`openPop` 的双 rAF 迟迟不跑，`visibility` 就一直停在 `hidden`。
  面板一重绘即变 `visible`：35 个日格、`aria-expanded="true"`、定位在视口内。
  **预览器的假象，不是缺陷** —— 这也正说明日历的时序问题只能真机验。
- **`.nsdp-pop` 收起后内联 `display` 仍是 `block`** —— `date-picker.css:110` 的基态是 `display: none`，
  收起时 `closePop` 写的内联值生效；我看到的是 `visibility: hidden` 的那一帧。
  即便残留，`visibility: hidden` 不接指针、不进无障碍树。

**发现但没做（超出 polish 范围，应走 `/impeccable harden`）：**
`main.js:670` 的 `get-entries` 是 `event.reply('get-entries-success', readData())`，
而 `readData()` 在 JSON 损坏时 **catch 后返回 `[]`**（`main.js:96-99`）。
于是一个损坏的 `data.json` 在历史页显示成「共 0 条记录 / 暂无记录」——
**「你没有记录」和「我们读不出你的记录」在界面上长得一模一样**，

homepage 的统计走的就是 `{ error: true }`（`scripts/preview-mock.js:90` 在模拟它）。
